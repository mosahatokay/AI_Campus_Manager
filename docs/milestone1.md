# CampusAI — אבן דרך א׳: תיעוד תכנון, מצב וראיות

**קורס:** סוכני AI · **תאריך עדכון:** 24.11.2026 · **מגישים:** מוסא ונוריאן (נא לוודא שמות מלאים)

## 1. בעיה, ארכיטקטורה והחלטה בכל צעד

CampusAI מיועד למזכירה הראשית לתיאום חדרים, שיעורים ומבחנים לפי קיבולת, מחשבים, מקרן, תאריך והזמנות קיימות. מבנה הדוגמה: 120 חדרים סינתטיים (5 בניינים × 3 קומות × 8 חדרים). החוקים בקוד: ימי ראשון–חמישי, 08:00–22:00, התאמת קיבולת וציוד ובדיקת התנגשויות. בקשה עם תאריך וללא שעה מציגה חלונות זמינות; אין להמציא שעה.

**זרימת החלטה:** `model.choose(messages, tools)` מחזיר בחירת כלי או תשובה → `CampusAgent` מנהל לולאה (עד שישה צעדים כברירת מחדל) → `CampusTools` בודק חוזה JSON Schema, הרשאות וכללי פעילות → `MockBackend` או `SQLServerBackend` מחזיר תצפית → הסוכן מחליט אם להמשיך או לעצור. פעולת כתיבה היא תחילה **הצעה ממתינה**, ולא מתבצעת בעקבות הודעת צ׳אט. רק שכבת יישום מהימנה יכולה להעביר אישור מפורש ל־`agent.confirm(...)`; ה־backend בודק מחדש תנאים והתנגשויות בזמן הכתיבה. בדמו להגשה `ScriptedModel` קובע מראש את בחירות הכלים; זהו מבחן זרימה **ולא** הוכחה להבנת שפה חופשית.

**ששת הכלים:** `find_rooms`, `get_availability`, `list_exams` (קריאה בלבד); `create_reservation`, `cancel_reservation`, `update_reservation` (כתיבה באישור). כל החוזים בקובצי JSON נפרדים עם סכמות קלט ופלט, שגיאות והרשאות. שגיאת קריאה זמנית מאפשרת שני ניסיונות חוזרים נוספים (עד שלושה ניסיונות בסך הכול). כתיבה עם תוצאה לא ודאית **אינה** נשלחת שוב אוטומטית.

## 2. סכמת מצב וזיכרון

`CampusAgent.sessions` שומר אובייקט `Session` לכל `session_id`, עם `messages` (היסטוריה), `compact_dialogue` (תמצית דיאלוג), `memory` (עובדות מתוצאות כלים), `audit` (החלטות) ו־`pending` (הצעת שינוי ממתינה). בדיקות מאמתות ששיחות שונות אינן מתערבבות. המצב נשמר בזיכרון התהליך בלבד, ואינו נשמר לאחר הפסקת ההרצה.

**השוואה מבוקרת של אותה שאלה:** ״מה שם האירוע של ההזמנה שאושרה קודם?״ התשובה הצפויה: `Physics Midterm - Synthetic Test`. בשתי הרצות Mock זהות, לאחר ההזמנה ועוד שמונה פניות, קורא דטרמיניסטי בדק רק את המידע שהועבר לו:

| אופן ההקשר | הודעות | תווים ב־JSON | תוצאה |
|---|---:|---:|---|
| מלא (`full`) | 22 | 3,153 | זיהה נכון את שם האירוע |
| מצומצם (`compact`) | 8 | 1,960 | שם האירוע חסר; לא הומצאה תשובה |

הצמצום חסך כ־38% מתווי ההקשר אך איבד את שם האירוע; פרטי מספר הזמנה, חדר, תאריך ושעה נשמרו. **זו בדיקת שימור מידע ב־Mock (`VerifiedResultReader`), לא מדידת דיוק של LLM.** נתונים מלאים ב־`docs/context_comparison_results.json`.

## 3. בדיקות, עקבות ויכולת שחזור

**תוצאה מקומית שדווחה ב־24.11.2026:** `131 passed in 2.25s` ב־`python -m pytest -q`, עם הרצת `list_exams` מדומה וקריאה מוצלחת ב־SQL Server מקומי עבור הזמנת ניסיון מספר 8. נבדקו גם יצירה, ביטול ועדכון מול SQL Server מקומי בשלבים קודמים. **הרצה נקייה של 131 הבדיקות ב־Colab עדיין דרושה לפני ההגשה.** בדיקות היחידה הן ללא שירות חיצוני.

קובצי העקבות `docs/traces/success.json` ו־`transient_failure.json` נוצרים מהפעלת לולאת סוכן מדומה: בהרצה התקינה `get_availability` הצליח בניסיון אחד; בכשל הזמני ה־Mock נכשל שלוש פעמים והחזיר `service_unavailable` עם `retryable=true`. בשניהם נשארו שש הזמנות. הקבצים כוללים בקשה, החלטה, קריאת כלי, תצפית, תשובה ויומן החלטות. פקודות שחזור: `python -m src.context_comparison`, `python -m src.trace_examples`, ו־`python -m pytest -q`.

## 4. מגבלות, סטיות מההצעה ותרומת מגישים

ב־Colab משתמשים ב־`MockBackend`; ה־SQL Server מקומי ואינו תנאי לשחזור. אין ממשק מזכירה מלא או שמירת מצב שיחה לדיסק. ניסוי Qwen חינמי בחר `find_rooms` אך בהמשך החזיר פלט לא תקין; לא הושלמה שיחה חופשית מוצלחת. ביחס להצעת 11.11.2026: `list_exams` הושלם; `create_booking` ו־`modify_booking` מומשו בשמות אחרים ופוצלו ליצירה, ביטול ועדכון. בנוסף בקוד יש שני retries לקריאה (במקום אחד בהצעה) ושישה צעדי סוכן כברירת מחדל (במקום שמונה). אלה הבדלים שיש לתאר למרצה ולא להציג כאילו אושרו במפורש.

| מגיש/ה | תרומה שבוצעה ואומתה |
|---|---|
| מוסא | הגדרת הדרישות, ניהול ובחינת תוצרי פיתוח בסיוע ChatGPT, הרצות בדיקות מקומיות, ניסויי SQL Server, העלאות Git ו־Colab |
| נוריאן | **להשלמה על ידי המגישים לפי עבודה שנעשתה בפועל; אין לרשום תרומה שלא בוצעה** |

ראו `docs/ai_usage.md` לגילוי שימוש ב־AI. לפני ההגשה יש לאשר את שמות המגישים המלאים ואת טבלת התרומה.
